PASSATION — INTÉGRATION OLLAMA DANS STOCK_V2
=============================================
Ce fichier sert à reprendre le travail depuis une session Claude Code lancée
SUR LE VPS (garrix@157.173.103.147, projet dans ~/Stock_v2). Il résume ce qui
a été construit en local, ce qui reste à faire sur le serveur, et les pièges
connus. À lire en entier avant d'agir. Tout ce qui est décrit est commité sur
la branche main (voir "Étape 0" pour le push si ce n'est pas encore fait).

Contexte : Ollama tourne sur l'hôte du VPS (service systemd, User=ollama,
modèles qwen3:4b et qwen2.5:0.5b, CPU uniquement, 7,8 Go de RAM). Le backend
Django tourne dans Docker (docker compose, service `backend`, code monté en
volume `.:/app`). Un Ollama tourne aussi sur le PC de développement mais
l'utilisateur a demandé de NE PAS tester dessus : la cible est le VPS.


1. CE QUI A ÉTÉ CONSTRUIT
-------------------------

A) Fusion des fiches produit identiques lors d'un transfert
   - users/ai_matching.py : rapprochement déterministe (prix identiques
     ÉLIMINATOIRE, puis nom + référence + description normalisés) et, en
     repli, appel Ollama (/api/chat, format JSON schema, think:false) qui ne
     peut désigner qu'un candidat déjà filtré sur le prix.
   - users/views.py, TransferProductsView : les trois points de recherche de
     la fiche destination passent par find_destination_product (mémorisée
     par produit dans l'appel). Le transfert TOTAL fusionne désormais au lieu
     de déplacer une fiche en doublon ; la fiche source est vidée, jamais
     supprimée (Sale/Movement en CASCADE).
   - Réponse de POST /api/users/transfer/products/ enrichie : transfer_batch,
     matches[], merged_count, created_count (voir modifhistory.md).
   - Tests : users/tests_transfer_merge.py (8 tests, IA désactivée).

B) Assistant conversationnel (bulle en bas à droite, web + mobile)
   - users/assistant.py : boucle agent bornée (3 appels modèle max), outils
     de lecture (list_magasins, search_products, get_product,
     low_stock_products, stock_summary, sales_summary, recent_movements) et
     outils de modification (adjust_stock, update_prices, transfer_product).
     RÈGLE : une modification n'est JAMAIS exécutée par le modèle. Le backend
     renvoie une "pending_action" (description + jeton signé
     django.core.signing, 15 min) ; le client affiche Confirmer ; puis
     POST assistant/execute/ avec le jeton. Chaque action confirmée crée un
     Movement (note préfixée "Assistant IA").
   - Endpoints : POST /api/users/assistant/chat/ et
     POST /api/users/assistant/execute/ (users/urls.py).
   - Périmètre = même règles que les vues REST (admin : magasins de la
     société ; gérant : son magasin ; employé : son magasin, lecture seule).
   - Frontend Next.js : components/assistant-bubble.tsx monté dans
     app/(app)/layout.tsx ; client dans lib/django-client.ts (assistant.chat,
     assistant.execute). Conversation en sessionStorage.
   - Flutter (valhery_wear) : lib/data/repositories/assistant_repository.dart,
     lib/state/assistant_provider.dart, lib/features/assistant/assistant_bubble.dart,
     monté dans lib/widgets/navigation_shell.dart (Stack + FAB). Timeout Dio
     dédié de 4 min sur ces deux appels.
   - Tests : users/tests_assistant.py (11 tests, modèle simulé).

B bis) Guide d'utilisation servi par l'assistant (18/09/2026)
   - users/guide.py : charge users/guide_content.json, filtre par rôle,
     recherche tolérante (accents, racines tronquées, synonymes métier :
     vendre→vente, transférer→transfert…), renvoie au plus 2 sections /
     4 000 caractères.
   - users/guide_content.json : GÉNÉRÉ, ne pas éditer à la main. Source de
     vérité = frontend/app/(app)/aide/guide-content.ts (la page /aide).
     Régénérer après toute modification du guide :
        node --experimental-strip-types scripts/export_guide.ts
     Un test (tests_guide) échoue si les deux sont désynchronisés.
   - users/assistant.py : nouvel outil de lecture `guide_app(sujet,
     section_id)` offert à tous les rôles. Le prompt système ne contient plus
     que le SOMMAIRE du guide (une ligne par section, filtré sur le rôle,
     ~1 000 tokens au total pour un admin) ; le texte complet n'est chargé
     que si le modèle appelle l'outil. L'ancien bloc « comment faire » codé
     en dur a été supprimé : il divergeait déjà du guide (il parlait d'une
     « invitation par email » qui n'existe pas dans l'app).
   - frontend/components/assistant-bubble.tsx : puces de démarrage affichées
     tant que la conversation est vierge, adaptées au rôle, deux familles
     (guide en indigo, données en vert). Un clic envoie la question.
   - Tests : users/tests_guide.py (14 tests).

C) Configuration
   - Stock/settings.py : OLLAMA_URL (défaut http://172.18.0.1:11434),
     OLLAMA_MODEL, OLLAMA_TIMEOUT, AI_PRODUCT_MATCHING_ENABLED,

3. PIÈGES CONNUS
----------------
- 127.0.0.1 dans un conteneur = le conteneur. Ollama doit écouter sur
  172.18.0.1 (passerelle du réseau compose stock_v2_default, épinglée
  dans docker-compose.yml) ; c'est le sens du drop-in systemd.
- Après le drop-in, la CLI `ollama` de l'hôte a besoin de
  OLLAMA_HOST=172.18.0.1:11434 (ajouté à /etc/environment par instructions.md).
- qwen3 "réfléchit" par défaut : think:false est envoyé, avec repli sans le
  champ si le modèle ne le supporte pas (HTTP 400).
- Le premier appel après inactivité recharge le modèle (2,5 Go) : d'où
  OLLAMA_KEEP_ALIVE=30m.
- Un déploiement concurrent (`docker compose up -d --build` depuis un autre
  terminal) a déjà provoqué des conteneurs "Dead" pendant une intervention :
  vérifier `ps aux | grep "docker compose"` avant de toucher aux conteneurs.
- La suite de tests historique users/tests.py a 2 à 5 échecs PRÉ-EXISTANTS
  (add-admin 403, upload de logo), instables d'un run à l'autre, sans rapport
  avec ces changements. Ne pas chercher à les corriger dans ce cadre.
- Les .pyc de __pycache__ sont suivis par git dans ce dépôt : ne pas les
  ajouter aux commits.

5. ÉTAT CONSTATÉ SUR LE VPS — session du 18/09/2026
---------------------------------------------------

Ollama n'a PAS été réinstallé : le service était sain. Le blocage venait du
pare-feu. Ce qui a été fait :

A) CAUSE DE LA PANNE « le conteneur ne joint pas Ollama »
   UFW a été activé sur le VPS APRÈS la mise en place d'Ollama (la version
   précédente de ce fichier affirmait « aucun pare-feu actif » — c'était vrai
   à l'époque, plus maintenant). Politique `deny (incoming)` par défaut, et
   11434 absent de la liste des ports autorisés. Le trafic conteneur →
   passerelle Docker traverse la chaîne INPUT de l'hôte : il était donc jeté.
   Symptôme trompeur : TIMEOUT et non « connection refused ».
   Test qui tranche : depuis le conteneur, le port 22 de l'hôte se connecte
   en 0,00 s, le 11434 timeout → réseau Docker sain, c'est UFW.

   Correction (persistante, voir instructions.md § 1 bis) :
     sudo ufw allow from 172.18.0.0/16 to 172.18.0.1 port 11434 proto tcp
   Vérifié : stock_backend OK en 0,03 s ; réseau ecoliko (172.19) bloqué ;
   IPv4 et IPv6 publiques bloquées.

B) ADRESSE DE BIND — la doc disait 172.17.0.1 (docker0), le déploiement réel
   utilise 172.18.0.1 = passerelle du réseau compose `stock_v2_default`,
   épinglée dans docker-compose.yml. Toute la doc a été corrigée.

C) DROP-IN SYSTEMD réécrit, + /etc/systemd/system/ollama.service.d/
   10-docker-order.conf ajouté (After=docker.service) : sans cet
   ordonnancement, Ollama démarrait avant que dockerd ait créé le réseau et
   échouait à se binder. Ajouté aussi OLLAMA_NUM_PARALLEL=1 et
   OLLAMA_MAX_LOADED_MODELS=1 (7,8 Go de RAM, aucun swap).
   OLLAMA_HOST=172.18.0.1:11434 ajouté à /etc/environment (il n'y était pas) :
   la CLI `ollama` fonctionne désormais dès la connexion SSH.
   Sauvegardes : override.conf.bak-*, /etc/ufw/user.rules.bak-*.

D) PERFORMANCE — MESURES APRÈS LIBÉRATION D'ESPACE DISQUE
   Le disque est passé de 81 % à 31 % d'occupation (101 Go libres). Mesures
   refaites à l'identique depuis stock_backend, machine au repos :

                      AVANT (disque 81 %)      APRÈS (disque 31 %)
     qwen3:4b         0,48 tok/s               1,54 tok/s    (x3,2)
     qwen2.5:0.5b     2,25 tok/s               4,01 tok/s    (x1,8)
     qwen3:4b à froid 108 s (load 22 s)        81 s (load 17 s)
     qwen3:4b à chaud 256 s                    111 s

   LE GOULOT DISQUE A DISPARU. vmstat pendant l'inférence, avant/après :
     avant : us 18 %  | id 45-75 % | wa 16-35 % | bi/bo élevés
     après : us 93-97 % | id 0-4 %   | wa 0 %     | bi/bo ≈ 0
   La machine est maintenant réellement limitée par le CPU. 1,54 tok/s est
   donc le PLAFOND de qwen3:4b sur ces 4 vCPU : plus rien à gagner côté
   disque ou RAM. Pour aller plus vite il faut changer de modèle, réduire le
   nombre de tokens générés, ou plus de CPU.

   Conséquences sur les réglages actuels — TOUJOURS INADAPTÉS :
     rapprochement (num_predict=150) : ~100 s d'eval + prompt
        → OLLAMA_TIMEOUT=20 et AI_MATCH_TIME_BUDGET=45 échouent toujours.
     assistant (num_predict=600, jusqu'à 3 appels modèle) : ~390 s par appel
        → OLLAMA_ASSISTANT_TIMEOUT=120 échoue toujours.
   Valeurs cohérentes avec 1,54 tok/s si on garde qwen3:4b :
     OLLAMA_TIMEOUT=180, AI_MATCH_TIME_BUDGET=200, OLLAMA_ASSISTANT_TIMEOUT=600.
   Mais 6 min d'attente pour une réponse d'assistant reste inacceptable en
   usage réel : voir le point E, qui est le vrai levier.

   ⚠ Ne PAS régler OLLAMA_MODEL=qwen2.5:0.5b pour le rapprochement en gardant
   qwen3:4b pour l'assistant : avec OLLAMA_MAX_LOADED_MODELS=1, chaque
   alternance provoque une éviction + rechargement. Utiliser le MÊME modèle
   pour les deux usages, ou passer MAX_LOADED_MODELS à 2 en surveillant la
   RAM (3,2 + 0,6 Go, sans swap : risque d'OOM).

E) think:false EST IGNORÉ PAR qwen3:4b
   Le champ est bien envoyé (ai_matching.py:224, assistant.py:585) et Ollama

7. PANNE « SERVICE MOMENTANÉMENT INDISPONIBLE » — DIAGNOSTIC (18/09/2026)
--------------------------------------------------------------------------

A) Cause racine : OOM, pas le réseau
   Log backend : « Ollama injoignable (Remote end closed connection without
   response) ». Reproduit à la main : POST /api/chat qwen3:4b →
   HTTP 500 {"error":"llama-server process has terminated: signal: killed"}
   (runner tué par l'OOM killer), ou coupure de connexion quand c'est tout
   Ollama qui meurt (systemd le relance 3 s après). /proc/vmstat : oom_kill
   passé de 5 à 6 pendant les essais. 172.18.0.1:11434 répond parfaitement.
   RAM : 7,9 Go, 0 swap. Au moment de la panne, ~3,9 Go étaient pris par les
   serveurs IDE distants (vscode-server ×N, Antigravity, extensions Claude
   Code) : ~2,6 Go disponibles, insuffisant pour qwen3:4b (2,5 Go de poids +
   ~1 Go de cache KV à num_ctx 8192). Même à num_ctx 4096 : tué.
   Un second Ollama (snap, v0.34.0, root, 127.0.0.1:11434, aucun modèle)
   tourne inutilement à côté du service systemd (v0.30.10, 172.18.0.1).

B) Ce qui a été corrigé dans le code
   users/assistant.py : _call_model distingue désormais les pannes et les
   journalise avec leur cause — HTTP 500 « killed » → mémoire ;
   RemoteDisconnected → Ollama mort en cours de requête ; TimeoutError →
   modèle trop lent ; URLError → injoignable ; 404 → modèle absent. La vue
   renvoie {"error": <message adapté>, "reason": <code>} en 503.
   _strip_thinking retire un bloc <think> résiduel de la réponse.
   frontend/lib/django-client.ts : lit la clé `error` (convention du
   backend) au lieu d'afficher « error: … ».
   Tests : users/tests_assistant.py, 7 tests ajoutés (18 au total, OK).

C) Matrice des modèles, mesurée depuis stock_backend avec la vraie
   run_conversation (utilisateur 51, magasin 13), machine chargée (load ~4,5) :

     modèle         RAM chargé  tok/s  stock (lecture)   guide        action
     qwen3:4b       ~3,3 Go     1,5    OOM               OOM          OOM
     qwen3:1.7b     2,4 Go      2,0    n'appelle l'outil qu'avec think:true
                                       (+100 tokens de raisonnement ≈ 50 s)
     qwen2.5:1.5b   1,4 Go      ~3     INVENTE un chiffre INVENTE      invente l'id
     qwen2.5:0.5b   0,6 Go      ~4     OK (33 s)         INVENTE      invente l'id

   « invente » = répond sans appeler l'outil, malgré le prompt. Sur l'action,
   0.5b et 1.5b passent un product_id fantaisiste sans search_products :
   le garde-fou de prévisualisation rejette, aucun dégât.
   qwen3:1.7b et qwen2.5:1.5b ont été tirés pour ces essais et laissés sur
   le disque (ollama rm pour les retirer).

D) Conclusion
   Sur ce VPS (4 vCPU, pas de GPU, 8 Go partagés avec deux stacks applicatives
   et les IDE distants), aucun modèle local ne donne un assistant à outils
   à la fois fiable et réactif. Le 4b est le seul à suivre les consignes mais
   il faut ~3,5 Go libres et il tourne à 1,5 tok/s (minutes par réponse).
   Pistes, par ordre de préférence :
     1. Basculer l'assistant sur une API hébergée (modèle rapide avec appel
        d'outils natif) : seule option qui règle à la fois la RAM, la vitesse
        et la fiabilité. _call_model est le seul point à adapter.
     2. À défaut, hygiène machine : swapfile 4 Go (évite l'OOM, ne règle pas
        la lenteur), fermer les sessions IDE inutiles, retirer le snap ollama,
        OLLAMA_ASSISTANT_TIMEOUT=600, et accepter des réponses en minutes.
     3. Sinon AI_ASSISTANT_ENABLED=False (la bulle affiche alors une erreur
        503 « désactivé » : le frontend ne masque pas encore la bulle).
